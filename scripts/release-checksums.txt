# BitFinite Core release checksums — the pin the upgrade scripts verify against.
#
# TWO KINDS OF ENTRY, and the distinction matters:
#
#   ARCHIVE lines (…tar.gz / …zip) are ADVISORY. An archive hash changes if the
#   artifact is merely re-tarred — different member order, different mtimes —
#   even when every binary inside is identical. That is not hypothetical: the
#   v3.1.0 tag triggered .github/workflows/build-core.yaml, CI rebuilt and
#   replaced the assets, and the archive hash changed while all six Linux
#   binaries stayed byte-for-byte the same. A hard gate on the archive rejected
#   a perfectly good artifact.
#
#   BINARY lines (vX.Y.Z/<name>) are AUTHORITATIVE. This is what actually gets
#   installed and executed, so this is what must not change silently. Note the
#   archive also ships its own SHA256SUMS, but that travels inside the artifact
#   and therefore only attests to itself — it cannot detect a substituted
#   archive. These lines are reviewed in git, which is the point.
#
# Adding a release: publish it, download the PUBLISHED assets, and take the
# hashes from those — not from your local dist/, which may differ from what CI
# uploaded.
#
# Linux binaries are reproducible across machines (local Docker and GitHub
# runners produce identical bytes). Windows ones are NOT — PE headers carry a
# build timestamp — so the Windows pins describe the published CI build
# specifically.
